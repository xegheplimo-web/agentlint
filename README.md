# AgentLint

An open agentic website that audits other agentic websites. Built to the Open
Agentic Web MVP profile 0.2 for the Open Agentic Web Challenge.

Paste an agentic site's base URL — the folder that should hold
`agent-manifest.json`, optionally with a network name — and AgentLint fetches
the published files, validates them against the spec's minimum, and reports
exactly what it found. A CORS failure is a finding, not an error to hide; a
check that cannot run is reported `skipped`, never `pass`. The assistant
(network `agentlint`, front agent `conformance_analyst`, specialist
`spec_reader`) can run the same audit, explain what the spec requires, and
export or save reports.

## What's here

- `index.html`, `styles.css`, `audit.js` — the audit page, its state and the
  auditor itself. `audit.js` works in the browser and under Node.
- `site-actions.js` — the four `website_*` actions (see below).
- `site.js` — boots the browser runtime into the assistant section.
- `agentlint.hocon` — the network's source of truth (built, not hand-edited).
- `agentlint.network.json`, `bridge/`, `agent-mcp.json`, `.well-known/` —
  generated by `build_network.mjs`.
- `agent-manifest.json`, `links.json` — the published manifest and link bindings.
- `runtime/` — the unmodified patched nsDeploy/agentic-web browser runtime.
- `tests/` — Node tests (no LLM calls, fetch stubbed).
- `scripts/audit.mjs` — the same auditor runnable from Node, for CI or demos.
- `examples/broken-site/` — a deliberately broken agentic site to audit.

## Checks the audit runs

| check | what it proves |
|---|---|
| `manifest.fetch` | `agent-manifest.json` is fetchable, CORS-permitting, HTTP 200, valid JSON. Fetch/CORS errors are reported with the reason. |
| `manifest.fields` | `networks[]` entries carry `name`, `front_man`, `hocon`; `llm_router`, `peer_policy`, `allowed_peers` present; advisories for `deployment.mode`, `sample_queries`. |
| `network[<name>]` | Each `hocon` reference resolves (relative or absolute), fetches with CORS, parses, passes the runtime's own validator — plus unique names, function descriptions, instructions on every LLM agent, no executable-only definitions, front_man exists in the resolved network. |
| `peer.policy` | Every peer/MCP URL a network references passes the runtime's own `manifestAllowsPeer` — the exact silent breakage of "allowed_peers forgot an origin". Unused `allowed_peers` entries and open mode are advisories. |
| `links.json` | Required when named peer references exist; validates bindings. |
| `actions` | Declared action wiring: version 1, module and bridge present (bridges are framed same-origin by design, so no cross-origin fetch is attempted). |
| `peer.call` | **Off unless the visitor turns it on.** Calls the network through this runtime's own peer path — consent card, composition budgets and all — and reports whether it loaded and answered. |

Every finding names the exact field, the expected and actual values, and the
reason. The verdict is `pass` when no check fails, `fail` otherwise, with a
one-paragraph summary and a machine-readable report (`export_report` /
`scripts/audit.mjs`).

## The four website actions

| action | effect | what it does |
|---|---|---|
| `get_audit_state` | read | current URL under audit, last report, history, saved directory |
| `run_audit` | write | `{url, network?, callPeer?}` — runs checks 1–5 (+ optional live call), stores and returns the report; `{ok:false, reason}` for non-http(s) URLs |
| `export_report` | read | the last report serialized as JSON; refuses when none exists |
| `save_to_directory` | write | appends the last report's summary to the local directory; dedupes |

## Running it

Static hosting only — no server code, no build step at runtime.

```shell
# build + check the network and generated files
node scripts/build_network.mjs agentlint.hocon --manifest agent-manifest.json --check

# tests
node --test "tests/*.test.mjs"

# serve locally (adds Access-Control-Allow-Origin to the public files)
node scripts/serve_site.mjs . --port 8099

# audit a site from the CLI (same code the page runs)
node scripts/audit.mjs http://127.0.0.1:8098 pizza_restaurant_website_assistant
```

No install step: everything runs on Node 22+ with no dependencies.

## What was verified

- **End-to-end in a real browser** (Playwright, real CORS enforcement between
  `http://127.0.0.1:8099` and the target): the page loads, the runtime boots, a
  conforming site (the reference pizza example on `:8098`) reports **PASS** with
  2 advisories + 1 skipped; a deliberately broken site (`examples/broken-site/`
  on `:8097`) reports **FAIL** with the exact fields (`allowed_peers`,
  `agent "helper".instructions`, `networks[0].front_man`, plus the disallowed
  peer origin). A cross-origin fetch to a 404 `links.json` appears honestly as
  a CORS-blocked skipped check.
- **End-to-end via `scripts/audit.mjs`** against the same servers, including a
  clean self-audit of AgentLint (6 pass, 0 advisories).
- **Unit/integration** under `node --test` (18 tests): network validity,
  action registration, URL refusals, PASS/FAIL fixtures, CORS findings, peer
  policy mismatch, the live-call path through `dispatchToolCall` with a stubbed
  engine, declined consent → skipped, export/directory semantics, consent-card
  focus handling.
- `node build_network.mjs ... --check` exits 0; all generated files are built,
  not hand-edited.

## Limits — read these before trusting a report

- **Static hosting only.** No server-side anything; reports live in page state
  (memory), so they do not survive a reload. `save_to_directory` keeps summaries
  in the same page state.
- **CORS is the gate.** Cross-origin audits run entirely on what the target's
  published headers allow — which is the point. In a browser a blocked fetch is
  reported as "fetch failed (CORS or unreachable)" because the two are
  indistinguishable by design; under Node (no CORS) the raw
  `Access-Control-Allow-Origin` header is the evidence. A same-origin fetch
  sees the true header.
- **The live call needs the runtime + a key.** `peer.call` is skipped unless
  the visitor enables it, the assistant runtime booted, and an AI provider key
  (or the mock router) is configured. Consent is asked first, per contact;
  declining reports `skipped`. The call runs the peer in the visitor's browser
  on the visitor's key — AgentLint never receives it.
- **No timeouts on the runtime's peer fetch** — a peer that never responds can
  leave a live call waiting; the audit itself is unaffected.
- **What the agent cannot answer.** It reports only what the published files
  and the live call actually did. It cannot judge whether a site is honest or
  safe, run an audited site's actions, see private data, audit a site with no
  `agent-manifest.json`, or reach past a login/paywall. `spec_reader` answers
  only from the spec requirements embedded in the published network file — if
  the spec does not cover something, it says so.
- **Not checked:** whether the target's *own* agents behave well at run time
  (beyond the single optional live call), action schemas inside
  `site-actions.js` files (never fetched cross-origin — bridges are framed, not
  fetched), `.well-known` contents, MCP endpoint liveness, or anything behind
  authentication.

## Notes

- The one `--check` warning, `peer_rules differs from templates/network.hocon`,
  is a line-ending artifact of the CRLF checkout: the texts are byte-identical
  after normalization; no error, exit 0.
